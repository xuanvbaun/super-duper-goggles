要，尤其是你说的这种 **电脑端 ChatGPT → Work → Codex** 流程，规格仍然值得有。

原因很简单：Work 可以沿用 Project 上下文，但 **Codex 仍是独立视图，历史记录也和 ChatGPT/Work 分开**。它可以直接操作本地文件夹、仓库、终端和开发工具，但你不能默认它自动知道我们这里所有已经讨论过的规则。

所以最合适的方式不是写一份几十页需求书，而是做一份 **“项目总规格 + Codex 执行入口文件”**。以后你从我这里转 Codex，基本只需要告诉它：**“按项目规格继续执行。”**

下面这版就可以直接作为第一版。

# 个人 AI 工作流调度平台 V1

## 1. 项目目标

开发一个仅供个人使用的 AI 工作流调度平台。

用户只通过一个统一入口提交自然语言任务，系统负责：

用户需求  
→ 判断任务类型  
→ 拆解任务  
→ 选择执行器  
→ 执行任务  
→ 自动检查  
→ 总控验收  
→ 完成或返工

V1 的核心目标不是“支持所有 AI”，而是先验证：

**多个 AI、代码 Agent 和确定性程序是否能够稳定交接、执行和验收。**

---

# 2. V1 基本原则

## 2.1 开发原则

1. 先能运行，再优化。
2. 本地优先。
3. 单用户。
4. 不追求复杂架构。
5. 程序能确定完成的任务，不调用 AI。
6. 低成本 AI 能完成的任务，不调用高成本模型。
7. AI 不得自行宣布整个任务最终完成。
8. 所有重要操作可追踪、可回退。
9. 禁止无限自动重试。
10. 高风险操作必须经过用户确认。

---

# 3. V1 执行角色

## ChatGPT / 总控层

职责：

- 理解用户需求
- 判断真实问题
- 任务分类
- 任务拆解
- 制定执行方案
- 判断执行结果
- 技术验收
- 失败后重新规划

不主要承担大量重复执行任务。

---

## Codex / 代码执行层

职责：

- 阅读代码仓库
- 修改代码
- 新建代码文件
- 运行命令
- 执行测试
- 定位 Bug
- 重构
- 输出代码执行结果

Codex完成任务后只能返回：

**执行完成，等待验收。**

不能自行宣布整个用户任务已经完成。

---

## DeepSeek API / 低成本 AI 执行层

主要承担：

- 翻译
- 摘要
- 分类
- 文本提取
- 信息结构化
- JSON生成
- 批量文本处理
- 其他低风险、高频 AI 任务

原则：

如果任务属于大量、重复、低风险模型调用，优先 DeepSeek API。

---

## Python / 脚本 / 确定性执行层

主要承担：

- 文件处理
- Excel生成
- 数据计算
- 数据格式转换
- 自动检查
- 数据比对
- 固定规则
- 定时任务
- 已经确定逻辑的业务流程

原则：

**能够确定性解决的问题，不调用大模型。**

---

# 4. V1 暂不接入

V1 不主动接入：

- Claude
- Gemini
- Perplexity
- WorkBuddy
- Grok
- 其他模型

架构必须保留未来扩展接口，但不得因为未来扩展而增加当前复杂度。

# 5. 任务分流逻辑

收到任务后按照以下优先级判断：

```text
收到用户任务
      ↓
能否用确定性程序解决？
      ↓
   是 → Python / 脚本
      ↓否
是否主要涉及代码仓库？
      ↓
   是 → Codex
      ↓否
是否属于大量、重复、低风险 AI 文本任务？
      ↓
   是 → DeepSeek API
      ↓否
ChatGPT 总控处理
```

总原则：

```text
程序
↓
低成本模型
↓
代码 Agent
↓
高能力总控
```

具体执行器由任务性质决定，不机械套用。

---

# 6. 任务生命周期

统一状态：

```text
NEW
↓
PLANNED
↓
RUNNING
↓
VERIFYING
↓
REVIEW
↓
DONE
```

异常状态：

```text
FAILED
```

任务失败以后进入 REVIEW，由总控决定下一步。

---

# 7. 自动重试机制

禁止 AI 无限自动修复。

规则：

### 第一次失败

允许当前执行器自动修复并重新执行一次。

### 第二次失败

任务返回总控层。

总控重新判断：

- 原方案是否错误
- 是否应该换执行器
- 是否需要修改任务拆分
- 是否需要用户信息

允许总控重新制定一次执行方案。

### 再次失败

停止自动执行。

状态：

```text
FAILED
```

向用户报告：

- 已完成内容
- 失败位置
- 错误信息
- 已尝试方案
- 推荐下一步

```json
  "updated_at": ""
}
```

每个执行器必须报告：

```text

```

# 13. 验收体系

机器能够检查的内容优先自动检查。

机器无法可靠判断的内容交给总控。

最终业务决定由用户拍板。

---

## 代码任务

至少检查：

```text
程序是否可以运行
测试是否通过
是否出现异常
原有功能是否被破坏
输出是否达到任务目标
```

---

## Excel / 数据任务

至少检查：

```text
字段
数量
关键数据
公式
格式
源数据对应关系
文件能否正常打开
```

---

## 文件操作

检查：

```text
文件是否成功生成
文件是否可以正常打开
目标路径是否正确
原文件是否保留
输出是否完整
```

---

## AI文本任务

根据任务检查：

```text
信息是否完整
格式是否合法
JSON是否可解析
是否明显偏离原文
关键字段是否缺失
```

# 24. Codex 开发要求

Codex在开发过程中遵守：

1. 不擅自扩大需求。
2. 优先完成最小可运行版本。
3. 不为了“更高级”主动增加架构复杂度。
4. 每完成一个阶段必须运行测试。
5. 修改前先理解已有代码。
6. 不确认的问题不要自行创造业务规则。
7. 出现歧义时优先保留现有行为。
8. 所有修改必须可追踪。
9. 不执行不可逆高风险操作。
10. 每轮工作结束输出：

```text
本轮完成
修改文件
测试结果
未完成内容
发现的问题
下一步建议
```

# 26. 核心目标

整个项目始终围绕一个目标：

**让用户只负责提出目标和最终拍板，其余任务能够在总控 AI、专业 AI、代码 Agent 与确定性程序之间可靠地流转、执行、验证和交付。**

如果某个功能不能明显提高：

- 稳定性
- 自动化程度
- 交接可靠性
- 验收可靠性
- 用户操作效率

则暂不加入 V1。

这份已经足够当 **Codex 的项目总规格**。

而且我建议你真正转到电脑端以后，不要把整段聊天重新复制过去。最干净的做法是把这份规格保存到项目根目录，例如：

`PROJECT_SPEC.md`

再让 Codex 先做第一件事：

> 阅读 `PROJECT_SPEC.md`，不要直接开发完整平台。先检查规格是否存在技术冲突，然后按照第19节只建立第一阶段最小可运行骨架。不要擅自扩展范围。完成后运行测试并汇报修改文件、测试结果、未完成内容和发现的问题。

这样 Codex 得到的是**稳定的项目事实来源**，而不是靠聊天上下文猜。

另外，从现在的 ChatGPT 产品结构来说，**Work 更适合跨文件、研究、成品交付等多步骤工作；Codex 专门负责代码、仓库、命令和测试**，所以以后这个项目的合理工作方式很可能就是：**我们这里定规则/审查 → Work处理跨文件工作 → Codex真正开发代码。** 

以后规格变化，也不要重写整个提示词，直接更新 `PROJECT_SPEC.md` 即可。这样你换模型甚至换 AI，项目规则也不会跟着丢。
